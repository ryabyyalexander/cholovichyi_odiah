# Этап 5: Поддержка медиа в MessageService

На этом этапе был расширен `MessageService` для полноценной работы с медиа-контентом (фото, видео), что является ключевым шагом к восстановлению полного функционала старого бота на новой архитектуре.

## Реализация

### 1. Расширение `MessageService`

В класс `MessageService` (`app/services/message_service.py`) были добавлены два основных метода:

- **`send_media(...)`**:
  Универсальный метод для отправки и управления медиа-сообщениями. Его логика повторяет принципы `send_message`, но адаптирована для медиа:
    - **"Умное" редактирование**: Если предыдущее активное сообщение также было медиа, сервис пытается плавно его изменить с помощью `bot.edit_message_media()`. Это позволяет менять фото на фото или видео на видео без мерцания.
    - **Безопасная замена**: Если редактирование невозможно (например, предыдущее сообщение было текстовым), сервис сначала отправляет новое медиа-сообщение и только после этого удаляет старое.
    - **Обработка файлов**: Метод автоматически определяет, что ему передано — локальный путь к файлу или `file_id` из Telegram, — и использует соответствующий тип (`FSInputFile` или `str`).
    - **Обновление состояния**: После отправки в БД и FSM сохраняется новый тип контента (`'photo'` или `'video'`).

- **`edit_caption(...)`**:
  Вспомогательный метод, который позволяет быстро и эффективно изменить только подпись (`caption`) у уже отправленного медиа-сообщения, используя `bot.edit_message_caption()`.

### 2. Интеграция и Тестирование

Для немедленной демонстрации и тестирования нового функционала был обновлен обработчик команды `/start` (`app/handlers/common.py`):
- Теперь вместо текстового сообщения он отправляет приветствие с фотографией, используя `message_service.send_media()`.

### 3. Оптимизация скорости

В ходе тестирования была выявлена медленная скорость ответа команды `/start`. Анализ показал, что это было связано с большим размером исходного файла фотографии (~2 МБ), который загружался на серверы Telegram при каждом вызове.

Проблема была решена заменой файла на изображение значительно меньшего размера (~20 КБ). Это подчеркнуло важность оптимизации медиа-контента и показало потенциальное направление для дальнейшего улучшения — кэширование `file_id` после первой загрузки, чтобы избежать повторных загрузок одного и того же файла.
