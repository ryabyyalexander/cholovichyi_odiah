# Этап 4: Реализация "Режима чистой ленты" (Message Service)

На этом этапе была спроектирована и реализована одна из ключевых особенностей бота — система управления сообщениями, создающая эффект "одноэкранного приложения" или "чистой ленты". Это позволяет избежать замусоривания чата и делает взаимодействие с ботом более похожим на работу с графическим интерфейсом.

## Архитектура

Система состоит из нескольких взаимосвязанных компонентов, соответствующих принципам модульной архитектуры.

### 1. Модель данных (`app/db/models.py`)

В модель `User` были добавлены два поля для отслеживания "активного" сообщения:
- `active_msg_id` (BigInteger): Хранит ID сообщения, которое в данный момент является главным на экране пользователя.
- `active_msg_type` (String): Хранит тип контента этого сообщения (`text`, `photo` и т.д.). Это необходимо для "умного" редактирования.

### 2. Репозиторий (`app/db/repositories/user.py`)

`UserRepository` был расширен для работы с новыми полями. Он инкапсулирует всю логику взаимодействия с таблицей `users` в базе данных. Ключевые методы:
- `get_or_create`: Регистрирует нового пользователя или возвращает существующего.
- `update_message_info`: Атомарно обновляет `active_msg_id` и `active_msg_type` для конкретного пользователя.

### 3. Сервис (`app/services/message_service.py`)

`MessageService` — это ядро системы. Он содержит всю бизнес-логику по управлению сообщениями:
- **Получение активного сообщения**: При инициализации сервис пытается найти `active_msg_id` сначала в FSM (кэш), а затем в базе данных.
- **Отправка/Редактирование**: Метод `send_message` реализует основную логику:
    1. Проверяет, было ли предыдущее сообщение текстовым.
    2. Если да, пытается его **отредактировать** (`bot.edit_message_text`).
    3. Если редактирование невозможно (например, сообщение было с фото или его удалил пользователь), он **отправляет новое** сообщение (`bot.send_message`).
    4. После успешной отправки нового сообщения, он **удаляет старое**.
- **Обновление состояния**: После успешной отправки или редактирования сервис обновляет `active_msg_id` и `active_msg_type` в FSM и в базе данных через `UserRepository`.

### 4. Middleware (`app/middlewares/message_middleware.py`)

`MessageServiceMiddleware` выполняет роль "инжектора зависимостей". Он срабатывает на каждое входящее сообщение или колбэк и:
1. Создает экземпляр `UserRepository`, используя пул сессий.
2. Создает экземпляр `MessageService`, передавая ему все необходимые зависимости (`bot`, `state`, `user_repo` и т.д.).
3. Помещает созданный `message_service` в словарь `data`, делая его доступным внутри хендлеров.

### 5. Интеграция (`main.py` и `app/handlers/common.py`)

- Middleware был зарегистрирован в `main.py`, чтобы он применялся ко всем обновлениям.
- Обработчик `handle_start` был переписан для использования `MessageService`. Теперь вместо `message.answer()` он вызывает `message_service.send_message()`, делегируя ему всю работу по отображению сообщения.

## Результат

В результате этих изменений команда `/start` теперь работает в режиме "чистой ленты". Вся сложная логика инкапсулирована в сервисах и мидлварях, а хендлеры остаются "тонкими" и отвечают только за бизнес-логику конкретной команды, не заботясь о том, как будет отправлено сообщение.

1. Подробная логика "Менеджера сообщений"

  Основная цель этой системы — создать в чате ощущение "одноэкранного приложения", где новый контент заменяет старый, а не накапливается в ленте.

  Ключевые компоненты:

   1. `MessageService` (`app/services/message_service.py`):
      Это "мозг" всей системы. Он отвечает за логику отправки, редактирования и удаления сообщений.

   2. Модель `User` в БД (`app/db/models.py`):
      Это "долговременная память". В ней хранятся два поля:
       * active_msg_id: ID последнего "главного" сообщения, которое отправил бот.
       * active_msg_type: Тип этого сообщения ('text', 'photo' и т.д.).
      Это позволяет боту "помнить" свое последнее сообщение даже после перезапуска.

   3. Middleware (`app/middlewares/message_middleware.py`):
      Это "фабрика-инжектор". Его задача — автоматически создавать и "внедрять" готовый к работе MessageService в каждый обработчик (хендлер), которому он нужен.

  Пошаговый сценарий работы:

   1. Пользователь отправляет команду, например, /start.
   2. MessageServiceMiddleware перехватывает это событие.
   3. Он создает экземпляр MessageService, передавая в него все необходимое: объект bot, state (FSM), chat_id, user_id и, что важно, UserRepository для работы с базой
      данных.
   4. Middleware передает этот полностью настроенный объект message_service в ваш обработчик handle_start.
   5. Внутри handle_start вы вызываете всего одну команду: await message_service.send_message("Привет!").
   6. Что происходит внутри `send_message`:
       * Поиск старого сообщения: Сервис ищет ID предыдущего "активного" сообщения (active_msg_id), сначала в кэше FSM, а если там нет — в базе данных.
       * Попытка "умного" редактирования: Если старое сообщение было текстовым и новое тоже текстовое, сервис попытается его плавно отредактировать (edit_message_text).
         Это самый эффективный способ, без мерцания.
       * Безопасная замена: Если редактирование невозможно (например, старое сообщение было с фото или его удалил сам пользователь), сервис сначала отправляет новое 
         сообщение.
       * Удаление старого: Только после того, как новое сообщение успешно отправлено, сервис удаляет старое. Это гарантирует, что у пользователя никогда не будет пустого
         экрана, если отправка по какой-то причине не удастся.
       * Сохранение состояния: Сервис обновляет active_msg_id и active_msg_type в базе данных и кэше FSM, чтобы при следующем действии пользователя снова знать, какое
         сообщение нужно менеджить.

  ---

  2. Как этим пользоваться?

  Архитектура специально сделана так, чтобы использование в обработчиках было максимально простым.

   1. Подключите Middleware: Убедитесь, что в main.py middleware зарегистрирован для нужного роутера:
   1     common.router.message.middleware(...)
   2     common.router.callback_query.middleware(...)

   2. Запросите сервис в хендлере: Просто добавьте message_service: MessageService в аргументы вашего обработчика. aiogram автоматически "внедрит" его благодаря работе
      middleware.

   3. Используйте: Вместо await message.answer(...) или await bot.send_message(...) просто пишите:

   1     @router.message(CommandStart())
   2     async def handle_start(message: Message, message_service: MessageService):
   3         # ... ваша логика ...
   4         await message_service.send_message("Ваш текст", reply_markup=kb)
   5         await message.delete() # Не забываем удалить команду пользователя
  Вам больше не нужно думать о том, редактировать или удалять, есть ли предыдущее сообщение и т.д. — сервис все делает за вас.

  ---

  3. Что перешло из старого бота, а что нет?

  Что мы взяли (философия и ядро):

   * Сама концепция "чистой ленты" и управления одним активным сообщением.
   * Принцип "сначала отправь новое, потом удали старое" для надежности.
   * Хранение ID сообщения в базе данных для постоянства между перезапусками.
   * Использование Middleware для автоматического внедрения менеджера в хендлеры.

  Что нового и что не используется (улучшения и отличия):

   * Четкое разделение слоев (Главное улучшение):
       * Старый бот: MessageManager напрямую обращался к базе данных (from data_base.models import data_base). Это смешивало бизнес-логику и логику доступа к данным.
       * Новый бот: Теперь у нас чистая архитектура:
           * MessageService (слой сервисов) отвечает за бизнес-логику.
           * UserRepository (слой репозиториев) отвечает за доступ к данным.
           * Сервис зависит от репозитория, а не от глобального объекта базы данных. Это делает код более тестируемым, гибким и понятным.

   * Обработка медиа (Пока не перенесено):
       * Старый бот: MessageManager был большим классом с множеством методов для разных типов контента (send_photo_message, send_video_message, edit_media и т.д.).
       * Новый бот: Наш MessageService пока реализует только базовую логику для текста. Мы сознательно не стали сразу переносить обработку фото и видео, чтобы сначала
         построить прочный фундамент. В будущем мы сможем легко расширить MessageService, добавив методы для работы с медиа, и они будут работать по той же надежной
         схеме.

  По сути, мы взяли лучшую идею из старого проекта и реализовали ее на новом, более профессиональном архитектурном уровне.
